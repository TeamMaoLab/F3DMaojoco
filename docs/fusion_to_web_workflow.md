# 从 Fusion 360 到 MuJoCo 到浏览器：闭环机构数字孪生全流程

> 2026-07-15 实战总结。把一个含双闭环的舵机四足单腿从 Fusion 360 设计模型，
> 变成 MuJoCo 里可求解/可碰撞检测的仿真模型，再变成浏览器里可交互驱动的 3D 腿。
> 记录每个阶段的方法、踩坑、关键决策，供后续项目复用。

---

## 全景：三阶段流水线

```
Fusion 360 设计                MuJoCo 离线求解               浏览器交互
┌──────────────┐  导出      ┌──────────────────┐  LUT    ┌──────────────┐
│ 装配体+关节   │ ────────→ │ 运动学树+闭环约束 │ ──────→ │ Three.js 3D腿 │
│ +COL_碰撞体   │  JSON+STL │ +碰撞体+FK求解   │  JSON   │ +解空间地图   │
└──────────────┘           └──────────────────┘         └──────────────┘
 component_                  leg.xml + fk_newton         workspace_lut.json
 positions.json              + gen_workspace_lut         app.js + viewer.js
```

**核心思路**：不在浏览器里做实时运动学求解（闭环太难），而是**离线把解空间算好存成查找表（LUT）**，浏览器只做查表+插值+渲染。这样网页响应快、行为稳定、可离线。

## 阶段一：Fusion 360 导出

### 导出什么
- `component_positions.json`：每个零件的世界变换矩阵（4×4）+ 关节定义（revolute 类型、连接的两个 occurrence、关节点坐标）
- `stl_files/`：每个零件的 STL 网格（毫米单位）
- 碰撞体：用 `COL_` 前缀命名的组件，导出脚本自动提取圆柱几何（半径、长度、端点）

### 关键决策：碰撞体用命名约定而非自动生成
- **问题**：从 STL 网格反推碰撞体会不准（凸包过大、形状不符）
- **方案**：在 Fusion 里手动建 `COL_XXX` 圆柱组件代表碰撞体，导出脚本按命名前缀提取
- **好处**：碰撞体形状/位置完全可控，与实际机械限位一致

### 踩坑
1. **Fusion BRepFace API**：`face.surfaceType` 不存在，要用 `face.geometry.objectType`，且 objectType 带命名空间前缀 `adsk::core::Cylinder`，匹配时用 `endswith('Cylinder')`
2. **刚体信息丢失**：Fusion 的 Rigid Group（如大腿是 4 零件的刚体）导出脚本没读，需要在网页端硬编码刚体→零件映射
3. **多体组件**：一个 COL_ 组件可能有多个 body，要遍历所有 body 的所有圆柱面（不能只取第一个）

## 阶段二：MuJoCo 建模与离线求解

### 2.1 运动学树构建（leg.xml）

把 Fusion 的装配关系转成 MuJoCo 的 body 树。本机构是**双闭环平面机构**（XZ 平面运动，Y 是旋转轴）：

```
机架 ─[旋转1 @ J1]→ 膝盖动力发生器 ─[旋转6 @ J6]→ 膝盖传动1
                                    ─[旋转7 @ J7]→ 膝盖转动 ─[旋转4 @ J4]→ 膝盖传动2
机架 ─[旋转2 @ J2]→ 大腿刚体(4零件) ─[旋转3 @ J3]→ 小腿
```

MuJoCo 的 body 树只能表达开链，闭环要"砍断"成树 + 用 equality 约束补回：
- 砍断点 1：膝盖转动 ↔ 大腿（J2' 重合）
- 砍断点 2：膝盖传动2 ↔ 小腿（J5 重合）

### 2.2 纯运动学 FK 求解（fk_newton.py）—— 最关键的设计决策

**问题**：MuJoCo 自带的动力学约束求解器（equality connect + PD 控制）在闭环机构上有"局部解"问题——软约束会弹性变形，不同初值收敛到不同姿态，且动力学震荡难调。

**方案**：**完全不用 MuJoCo 的动力学/约束求解器**，只把它当 FK 引擎（`mj_forward` 算 body 世界坐标），自己写牛顿迭代解闭环：

```
输入: θ1, θ2（舵机角）+ 初值 x0=[t6,t7,t4,t3]（被动角弧度）
1. 锁定 qpos[θ1]=t1, qpos[θ2]=t2
2. 算约束残差 f (4维): 两个闭环 anchor 点的世界坐标差（x,z 分量）
3. 数值雅可比 J (4×4): 对每个被动角 +ε 扰动，重算 f，差分
4. 牛顿步: 解 J·dx = −f,  x += dx
5. 重复直到 ‖f‖ < 1e-8 (0.00001mm)
```

**为什么这样更稳**：得到的是精确解（残差 ~1e-12），不受 PD 增益/约束软硬度/阻尼影响。本质是把闭环约束当成非线性方程组直接解，而不是让物理引擎"平衡"出来。

### 2.3 最大的坑：闭环方程组有无穷多解

**现象**：同一个 (θ1, θ2)，牛顿迭代收敛后残差为 0（闭环确实闭合），但被动角出现 **t3=29917°**（连杆绕轴转了 83 圈）——这是**缠绕解**，数学上合法，物理上胡扯。

**根因**：闭环约束是三角函数方程（sin/cos），连杆可绕 Y 轴转任意整圈后让 anchor 重合。方程组有**无穷多解**，牛顿迭代只收敛到"离初值最近"的那个。**初值决定一切**。

同一个 (θ1=0, θ2=20)，不同初值给出 5 个完全不同的解：
```
t3初值=-180° → t3=-1460°  (缠绕)
t3初值= -90° → t3=  -20°  (正确)
t3初值=  +0° → t3=  -20°  (正确)
t3初值= +90° → t3= +227°  (错误分支)
t3初值=+180° → t3=-1100°  (缠绕)
```

### 2.4 解法：BFS 连续追踪 + 多初值 + 连续性选择

旧版生成 LUT 时每个点都从 `x0=0` 冷启动 → 少数点落到缠绕解。修复策略（gen_workspace_lut.py）：

1. **BFS 连续追踪**：从 (0,0) 种子（全 0 初值的正确解）出发，向四邻扩展，新点用已解邻居的解作初值（像 MuJoCo 交互拖滑块的连续性）
2. **多初值候选**：每点试 {邻居解, 零初值}，都解一次
3. **连续性选择**：在所有收敛解里，选与已解邻居关节角差最小的（阻止缠绕/错误分支入选）
4. **缠绕硬过滤**：任意被动角 |.|>360° 直接丢弃
5. **全局连续性平滑**（refine_continuity）：大范围扫描时不同区域锁不同分支，在距原点远的边缘产生跳变。从中心向外做多轮平滑，消除跳变

**效果**：±180° 范围 32761 格点全可达、零缠绕，跳变从 4095 处降到 474 处（剩余全在距原点 ≥88° 的边缘，是物理上真实的多构型分支）。

### 2.5 碰撞检测

- **碰撞体**：从 Fusion 的 COL_ 组件导出圆柱，写进 leg.xml 的 `<geom class="collider">`
- **父子 body 碰撞**：MuJoCo 默认不检测 parent-child body 碰撞，但本机构恰恰需要（如大腿↔小腿）。用 `<contact><pair>` 显式指定 collider geom 对参与碰撞
- **碰撞=硬限位**：舵机转到碰撞区就算限位，LUT 里标记 `collision: true`，网页端拖不进

### 2.6 连通性分析

解空间里有些区域"数学上可达但不连通"（被碰撞区隔开的孤岛）。从原点 flood fill 标记连通区域，孤岛标黄——**孤岛拖不到**（中间会穿墙），只有连通的绿色区可拖。

## 阶段三：浏览器交互

### 3.1 架构：LUT 驱动，无实时求解

- 加载 `workspace_lut.json`（θ1×θ2 网格，每点存 6 个关节角 + 碰撞/连通状态）
- 拖动时**双线性插值** 4 个角点的关节角，喂给 `viewer.applyJointRotations`
- `applyJointRotations`：按运动学树深度排序，父累积变换 × 相对旋转，逐零件应用

### 3.2 解空间地图（canvas）

θ1×θ2 二维地图，四色：
- 🟢 绿 = 可达且与原点连通（可拖）
- 🟡 黄 = 可达但不连通（孤岛，拖不到）
- 🔴 红 = 碰撞（限位）
- ⚫ 黑 = 不可达

### 3.3 连续拖动追踪

拖动不能瞬移（跳变很奇怪），要**一步步追过去**：
- `setTarget` 设目标，`stepTowards` 每帧小步（MAX_STEP=5°）追向目标
- 每步检查 `isAllowed`（可达 + 不碰撞 + 连通），红区/孤岛挡回
- 碰墙时尝试只走单轴（贴边滑动）

挂在 viewer 的 `onBeforeRender` 钩子上（渲染前更新姿态），避免双 requestAnimationFrame 不同步闪烁。

### 3.4 踩坑：渲染闪烁

**现象**：拖动时透视效果一闪一闪。

**排查过程**（按怀疑度排序）：
1. ❌ 双渲染循环 → 只有一个 rAF
2. ❌ matrixAutoUpdate 覆盖 → 已设 false
3. ❌ 每帧 fitCamera → 只在加载/点击时调
4. ✅ **半透明叠加**：材质 `transparent: true, opacity: 0.6`，半透明面渲染顺序每帧变化 → 混合结果闪烁
5. ✅ **深度缓冲精度**：`near=0.1, far=100000`（比值 100 万），零件毫米级落 在极窄深度区间 → Z-fighting

**修复**：
- 材质改不透明（`transparent: false, opacity: 1`），只留大腿盖板单独透明
- 收紧 near/far 到零件尺度（`near=1, far=2000`）
- 启用 `logarithmicDepthBuffer: true`（对数深度缓冲，远近同时清晰）

## 可复用的经验清单

### 架构层面
1. **离线求解 + LUT 驱动**：闭环机构不要在浏览器实时求解，离线算好查表。响应快、稳定、可离线
2. **纯运动学牛顿迭代**优于物理引擎动力学：闭环约束当非线性方程组直接解，不受 PD/软约束影响
3. **MuJoCo 当 FK 引擎**：只用 `mj_forward` 算世界坐标，不用它的约束求解器

### 求解器层面
4. **初值决定分支**：闭环三角方程有无穷多解，牛顿迭代收敛到离初值最近的。连续追踪（邻居解作初值）是关键
5. **缠绕解必须过滤**：检查被动角绝对值是否超阈值（如 360°）
6. **大范围要平滑**：±60° 内 BFS 够用，±180° 要加全局连续性平滑消除区域间分支切换
7. **多初值 + 连续性选择**比单初值鲁棒：每点试多个候选，选与邻居最连续的

### 渲染层面
8. **半透明是闪烁之源**：能用不透明就用不透明，必须透明时单独处理
9. **near/far 要匹配场景尺度**：比值超 1e5 就有 Z-fighting 风险
10. **logarithmicDepthBuffer**：r128+ 对 PerspectiveCamera 完全支持，彻底消除 Z-fighting

### 工程层面
11. **碰撞体用命名约定**（COL_ 前缀）：比从网格反推准确可控
12. **运动学树硬编码**：不追求通用解析，简单机构直接写死树结构 + 刚体→零件映射
13. **连通性分析**：可达 ≠ 可拖，要 flood fill 标记与原点连通的区域
14. **坐标系对齐**：grid[i][j] 存储方向 vs imshow 显示方向 vs canvas 绘制方向，三者容易转置错位，要数学验证
